# D-013 — Hosting Alternative: Friend-Provided Fly.io App

**Status:** Accepted
**Date:** 2026-08-01
**Decided by:** Project owner (explicit choice: friend-hosted Fly.io app)
**Supersedes:** D-006's *account ownership* only — the platform choice (Fly.io) is
unchanged, so D-006's technical content (Dockerfile, volume, release command, backups)
still stands. This doc records what changes: who owns the Fly organization the app lives
under.

## Decision

- **Host platform:** Fly.io (unchanged from D-006).
- **Account/org:** the Fly app is created under a friend's existing Fly.io
  organization/account, not the owner's own account.
- **App provisioning:** the friend creates the Fly app (name still `project-bct`, per
  D-006, assuming it's available in his org) and the persistent volume for
  `/data/bct.db`.
- **Deploy access:** the friend issues a **deploy-scoped** `FLY_API_TOKEN`
  (`flyctl tokens create deploy`, or the current equivalent — verify against Fly's live
  docs per D-006's existing "don't assume, verify" clause) and hands it to the owner.
  The owner controls CI/CD from there: this token goes into GitHub Actions repo secrets
  exactly as D-009 already specifies, and the `deploy` job in D-008's workflow uses it
  the same way it would with an owner-owned account. No change to D-008 or D-009's
  content — this is the scenario they were already written for.
- **Runtime secrets** (`APP_PASSWORD`, `SESSION_SECRET`, `DATABASE_URL`) are still set via
  Fly secrets on that app, by whoever has `fly` CLI access to it — confirm with the friend
  whether that's the owner directly or a request routed through him.

## Why

Owner has a friend willing to host on his existing Fly.io setup, avoiding new billing
signup while keeping the exact same technical target (Fly.io, Docker, persistent volume)
already accepted in D-006. A deploy-scoped token means the owner retains full control
over what gets deployed and when — the friend's involvement is infrastructure/billing
only, not operational control.

## Accepted risks

- **Dependency on a third party.** If the friend's Fly account lapses, gets suspended, or
  he withdraws the offer, the app's hosting disappears with it. No mitigation planned
  beyond the existing D-006 backup requirement (weekly offsite SQLite backup) — that
  backup is what makes a host change survivable, so it's not optional here.
- **Token provenance.** The owner is trusting a token generated by someone else's Fly
  account. Confirm on receipt that it's scoped `deploy` only, not a full personal token —
  don't assume based on what was asked for.
- **App name collision.** `project-bct` may already be taken globally on Fly (app names
  are global, not per-org) or the friend's org may have a naming convention — confirm the
  actual app name once created rather than assuming it matches D-006's plan verbatim.

## Consequences for the Builder

- No change to `Dockerfile`, `fly.toml` shape, or the CI workflow structure from D-006/
  D-008 — same artifacts, different account underneath.
- Do not attempt to run any `fly` CLI provisioning command yourself against the friend's
  account. App creation and volume setup happen on the friend's side, with the owner
  watching, per this project's standing rule that account-touching/irreversible actions
  happen with the owner present, not autonomously.
- Once the deploy token is received, treat it exactly per D-009's table — GitHub Actions
  secret, never committed, name matched exactly to what the CI workflow references.
- This is still gated behind Phase 7 (D-012) — nothing here changes when hosting actually
  gets built. Phase 2 (local scaffolding) proceeds now, unaffected.
